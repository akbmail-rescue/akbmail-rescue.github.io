# 敗因分析(ポストモーテム)— AKB48 Mail レスキューツール(2026-08-28)

## 結論
2026-08-26 に本ツール(画面収録+画像処理方式)を公開した同日、`lclaam/AKB48-Mail-Backup`(API 再現方式、Codex 製)が公開・SNS 共有され、目的達成度・完成度・拡散のすべてで先行された。オーナー判断により本プロジェクトは **ここで停止**(公開ページとリポジトリは残す)。以下は今後のアプリ技術選定・戦略策定のための記録。

## 事実
| | 本ツール | 相手 |
|---|---|---|
| 方式 | 画面収録 → フレーム分類 → pHash 代表選定 → 位相相関スティッチ → OCR(日時のみ) | mitmproxy で iPhone アプリの通信を捕捉 → 本人トークンで API から受信箱を直接取得 |
| 成果物 | メール画面の PNG(本文は画像、検索不可)+ metadata.json | 原本 HTML・原寸画像・JSON/CSV(検索可)+ IZPM 風ビューア・SHA-256 検証 |
| 取得時間 | 録画 2.4 秒/通 + 解析(実時間の 1〜7 倍) | 数分で全件、再開可能 |
| 対応環境 | ブラウザのみ、全 OS、スマホ単体可 | iPhone + Mac 限定、mitmproxy・証明書の導入が必要 |
| 規約面 | 本人が画面を録るだけ(最も安全) | 非公式 API 利用(証明書ピン止め対策・規約違反によるアカウント停止のリスク) |
| 公開 | 8/26 同日。告知なし | 8/26 同日。README・AI エージェント向け手順書つきで即共有 |
| 先行研究 | 未調査 | `okanikubay/AKB48GroupMailDownloader` を参照 |

## 敗因(重要度順)
1. **方式選択を検討せずに決めた**: 「画面収録しかない」という前提で要件書を書いた。アプリが API を使うか、先行ツールがあるかを着手前に調べていない。API 方式を採らない理由(BAN リスク)も文書化されておらず、比較検討が存在しなかった。**方式の差は後工程の努力で埋まらない**(劣化コピー vs 原本)。
2. **調査不足**: GitHub/SNS の 30 分の調査で先行研究と競合の芽は見つかった。
3. **「先に出す」より「固める」を優先した**: MVP 公開後の 2 日間を 7 回のレビュー・是正に使った。技術的には正しいが、勝負は同日に決まっていた。
4. **告知の準備がなかった**: 公開しただけで、対象ユーザーに届ける手段(SNS 投稿文・使い方動画・相手が対応しない Windows/Android 層への訴求)を用意していない。

## 今後の技術選定・戦略への教訓
- **着手前チェック(30 分)**: (1) 同目的のツール・先行研究を検索 (2) 対象アプリ/サービスの通信方式(公式 API / 非公式 API / 画面のみ)を把握 (3) 採り得る方式を列挙し、採らない理由を要件書に明記 (4) 先行がいれば「何で勝つか」を決めてから作る。
- **方式の優劣は成果物の質で決まる**: 原本データが取れる経路があるなら、画像処理は最後の手段。規約リスクで採れない場合は、その判断を明文化し、差別化(対応環境・導入の手間・安全性)を設計に織り込む。
- **時間配分**: MVP → 公開 → 告知 → 改善、の順。品質固めは公開後に回す。レビューは「出す前の致命傷確認」1 回に絞り、残りは反響を見てから。
- **公開と告知はセット**: 公開時点で、告知文・対象ユーザー・比較表(競合がいる場合)を用意する。
- **AI 製ツールの競争**: 相手も AI(Codex)製で同日に完成している。作る速度では差がつかない。差がつくのは「方式の選択」「調査」「出すタイミング」。

## 本プロジェクトの資産(再利用可能)
- ブラウザ内完結の動画→フレーム抽出(WebCodecs / ffmpeg.wasm フォールバック)、cv2 互換の位相相関、Pillow/imagehash 互換の pHash、IndexedDB 復元、Codex レビュー往復の仕組み(パケット生成・是正記録)。他の「画面しか取れない」対象(ブラウザ版メール、保存機能のないアプリ)に転用できる。
